# PasarPulse Deployment Demo — Codex Execution Packet

This folder is the implementation brief for turning the current PasarPulse research repository into a truthful, robust competition demo.

The key rule is simple: **deploy the project that exists now, not the neural/GNN system that was only proposed in the earlier paper.** The paper is retained as product and research context in `PAPER_CONTEXT.md`.

## Target demo

The demo should communicate this story in roughly 2–3 minutes:

1. Indonesia already has food-price monitoring; PasarPulse adds a **7-day and 14-day forward-looking warning layer**.
2. A user selects a commodity, market level, province, and historical forecast origin.
3. The app shows the price observed at the origin and the model forecast at +7/+14 days.
4. It converts projected price movement into a clearly labeled **product warning rule**, not a learned probability.
5. It shows available evidence/context and, only when real attribution artifacts exist, an explanation of model drivers.
6. Historical replay may reveal the later realized price, making leakage-safe evaluation intuitive to a judge.
7. A model-performance page shows validated metrics and clearly separates saved A100 architecture-search results from the compact executable finalist rerun.

## Runtime philosophy

The preferred first deployment is a modular Streamlit application with local cached artifacts.

```text
validated snapshot / replay artifact
              |
              v
       data-contract layer
              |
              v
    warning + evidence logic
              |
              v
       Streamlit dashboard
```

Training is offline. The application must not depend on Bapanas, PIHPS, ERA5, Sentinel, or other public endpoints being available during a live judging session.

## Data availability modes

The code must support three explicit modes and display the active mode in the UI:

### 1. Replay mode — preferred competition mode
Uses out-of-fold or holdout predictions created by the leakage-safe chronological evaluation. It can show forecast versus later realized value because this is a historical replay.

Preferred inputs, if present locally:
- `finalist_oof_predictions.csv` generated by `experiments/pasarpulse_notebook_finalist.py`;
- compatible saved architecture-search or deployment-shaped forecast artifacts;
- the model-ready panel only for contextual fields that were available as of the forecast origin.

### 2. Inference mode
Used only if actual serialized model artifacts plus a compatible latest feature snapshot are available. The UI must show model/data version and forecast-as-of timestamp.

### 3. Benchmark-only mode
Fallback when the repository only has the currently committed benchmark CSVs. The app still exposes project context, performance, methodology, and the snapshot data contract, but must not invent province forecasts.

## Definition of done

The MVP is complete when:

- `streamlit run demo/app.py` launches locally without GPU;
- the app resolves one of the three data modes deterministically;
- replay mode can show at least one real forecast if a valid replay artifact exists;
- missing replay/inference data produces an explicit informative empty state rather than synthetic claims;
- benchmark values are loaded from repository result files rather than duplicated as magic numbers where practical;
- warning logic has unit tests;
- snapshot schema validation has unit tests;
- a Docker image can build and start the app;
- no runtime step retrains models or fetches an upstream data source;
- no unsupported scientific claim is introduced by the UI.
